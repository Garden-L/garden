# Module delivery: source to verified code

Use when a vehicle module needs the whole result from supplied requirements through SRS, STS, issue resolution, bounded implementation, and evidence-based handoff. Apply shared `workflow-design` to preserve stage inputs, outputs, and checks. The project-specific output contract is [module deliverables](../../../docs/module-deliverables.md). Apply shared `decision` whenever a choice affects later artifacts. Keep one authoritative issue record and link it by ID; do not copy decisions into each document.

1. **Frame.** Apply `engineering-design`. Identify module boundary, source versions, target environment, responsible decision owner, and completion criterion. Create the module README and record unknowns. Do not guess safety levels or compliance.
2. **Specify.** Follow [requirements to SRS](requirements-to-srs.md) with `software-requirements-specification`. Produce `01-srs/SRS.md`, keep SRS-stage issues in `01-srs/issues.md`, and record source coverage and disposition in `01-srs/review.md`. Keep unapproved choices open.
3. **Design verification.** Follow [SRS to STS](srs-to-sts.md) with `software-test-documentation`. Produce `02-sts/STS.md`, explain applicable test design techniques, link every case to its source `REQ`, and record test-design review in `02-sts/review.md`. Keep STS-stage issues in `02-sts/issues.md`; an undefined expected result is a gap, not a passing test.
4. **Decide and reconcile.** Use `decision` for options, reason, owner, chosen response, and affected artifacts. If an approved baseline changes, follow [change control](change-control.md). Update SRS, STS, issue state, and traceability together. Preserve the old decision history.
5. **Check readiness.** Follow [readiness review](readiness-review.md). Record the verdict in `03-readiness/readiness-report.md`. Only work whose prerequisites and decisions are satisfied enters implementation planning.
6. **Plan implementation.** Follow [implementation planning](implementation-planning.md) to create ordered `04-implementation/WORK-<id>.md` packets and the traceability map. Each packet defines the behavior, exact boundary, test approach, dependencies, and stop conditions.
7. **Develop in units.** Select [feature](feature.md), [bug fix](bug-fix.md), or [refactoring](refactoring.md) for the change type, then execute [bounded implementation](implementation.md) for one eligible packet at a time. Record code, tests, commands, results, revision, and deviations in the packet.
8. **Integrate and review.** Follow [integration testing](integration-testing.md) when component or target interactions are in scope, then [code review](code-review.md) for the completed change.
9. **Verify and hand off.** Follow [implementation verification](verification.md) and [release readiness](release-readiness.md). Compare actual code and test runs with the SRS, STS, issue decisions, and evidence. Record environment limits in `05-verification/verification.md`. Generate `05-verification/completion-report.md` from traceability and verification records, inspect its gaps, then set the final verdict in the module README. A green structural validator or coverage count is not proof of behavior.

For a small module, combine stages in one work session, but preserve their decisions and outputs. For a large module, stop after any stage that lacks a responsible decision or required evidence and hand off the explicit next action. Never mark implementation or target verification complete because the corresponding document exists.
