# Automotive SRS Skill Design

## Intent

이미 작성된 문장 수준의 자동차 개발 요구사항을 실제 검토 가능한 SRS(Software/System Requirements Specification) 문서로 재구성한다. 원문을 단순히 옮기는 데 그치지 않고, 모호성·문맥 불일치·중복·검증 불가 문제를 식별하고 정제안을 함께 제시한다.

## Goals

- 불완전한 요구사항도 임의로 과장하지 않고 문서화한다.
- 요구사항을 식별 가능한 ID와 명확한 문장으로 정리한다.
- 기능 요구사항, 비기능 요구사항, 인터페이스, 제약사항, 검증 기준을 기본 섹션으로 제공한다.
- 모호하거나 문맥상 어색한 요구사항은 원문, 문제점, 정제 제안, 확인 필요 사항을 구분한다.
- 사용자가 제공하지 않은 정보는 `TBD`, `TBC`, 또는 확인 필요 항목으로 표시한다.

## Non-goals

- ISO 26262, ISO 21434, ASPICE 등의 표준 준수 여부를 판정하지 않는다.
- 안전 무결성 등급, 위협 모델, 상세 아키텍처를 임의로 결정하지 않는다.
- 구현 코드나 테스트 코드를 생성하지 않는다.

## Approach

사용자 입력을 SRS 템플릿에 맞춰 변환하고, 각 요구사항을 품질 검토한다. 각 요구사항은 가능하면 단일 의무사항을 담고, 검증 가능한 형태와 우선순위를 포함한다. 모호성이나 충돌을 해결할 근거가 없으면 확정하지 않고, 원문과 정제 제안을 나란히 제시한다.

## Output Structure

1. 문서 개요 및 목적
2. 범위 및 용어
3. 시스템/기능 개요
4. 기능 요구사항
5. 비기능 요구사항
6. 인터페이스 요구사항
7. 제약사항 및 가정
8. 검증/수용 기준
9. 요구사항 품질 검토
10. 정제 제안 및 확인 필요 사항
11. 미결사항 및 TBD 목록

## Builder Decisions

- 기본 출력은 Markdown SRS로 한다.
- 입력이 부족한 경우 긴 질의응답을 수행하지 않고, 문서 안에 미결사항과 정제 제안으로 남긴다.
- 자동차 도메인 용어는 입력에 있는 범위에서만 사용하며, 안전·보안 관련 주장은 별도 확인이 필요한 항목으로 표시한다.
- 원문을 확정 요구사항처럼 덮어쓰지 않고, `원문`, `정제된 요구사항`, `정제 이유`, `확인 필요`를 구분한다.
