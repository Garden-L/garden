# TICKER Rules Skill Design

## Intent

공통 문서·요구사항·이슈에서 사용하는 TICKER 식별자 원칙을 정의한다. TICKER는 항목을 안정적으로 참조하고 대화·문서·변경 이력을 연결하기 위한 식별자이며, 특정 문서 형식이나 업무 프로세스를 강제하지 않는다.

## Goals

- `REQ`, `ISSUE`, `BUG`를 포함해 여러 티커 유형을 일관되게 정의한다.
- 티커의 이름, 의미, 사용 위치, 참조 방법, 변경 원칙을 명확히 한다.
- STS/SRS에서 바로 적용할 수 있는 예시를 제공하되 다른 문서·프로젝트에도 일반화한다.
- 티커와 상태·우선순위·담당자 같은 운영 필드를 분리한다.

## Non-goals

- STS/SRS의 문서 구조를 강제하지 않는다.
- 특정 이슈 트래커, 저장소, 프로젝트 관리 도구 사용을 요구하지 않는다.
- 티커만으로 승인·배포·변경관리 프로세스를 자동으로 결정하지 않는다.
- 모든 조직의 티커 접두사나 상태 체계를 하나로 고정하지 않는다.

## Approaches considered

1. **단일 `ticker-rules` 스킬** — 공통 원칙과 대표 예시를 한 파일에 둔다. 가장 쉽게 발견·적용되고 현재 요구에 충분하다.
2. **핵심 스킬 + 상세 레퍼런스** — 티커별 필드와 상태 전이를 별도 문서로 분리한다. 확장성은 높지만 초기 사용에 비해 구조가 무겁다.
3. **정책 스킬 + 검증 도구** — 규칙과 함께 형식·중복·참조 누락을 검사한다. 자동화에는 좋지만 검증 대상 포맷과 실행 환경을 먼저 정해야 한다.

선택: **1번**. 현재는 범용 원칙이 목적이며, 검증 스크립트나 상세 레퍼런스는 실제 사용 중 규칙이 커질 때 별도 확장한다.

## Constraints

- 자동 선택 가능한 공용 스킬로 작성한다.
- `ticker-rules`는 소문자 하이픈 형식의 스킬 이름을 사용한다.
- 기본 규칙은 도구·저장소·문서 템플릿에 독립적이어야 한다.
- 티커 형식은 명확해야 하지만, 조직별 네이밍 정책을 덮어쓰지 않아야 한다.

## Intended rule shape

스킬은 다음을 포함한다.

- TICKER의 정의와 적용 판단 기준
- 권장 형식: `<TYPE>-<IDENTIFIER>` 및 조직별 접두사 확장 원칙
- 유형별 의미: `REQ`, `ISSUE`, `BUG`, `TASK`, `RISK`, `DECISION` 등
- 신규 티커 생성, 참조, 변경, 폐기 규칙
- 티커와 제목·상태·우선순위·담당자·문서 위치의 분리 원칙
- 모호하거나 중복된 티커를 발견했을 때의 처리
- STS/SRS를 포함한 요구사항 문서 예시
- 티커를 만들지 않아도 되는 경우

## Open implementation decisions

스킬 작성 시 기본값으로 다음을 사용한다.

- 티커는 문서 전체 또는 프로젝트 범위에서 유일해야 한다.
- 의미가 바뀌는 항목은 기존 티커를 재사용하지 않고 새 티커를 만든다.
- 티커는 짧고 안정적으로 유지하며, 제목이나 상태를 티커에 넣지 않는다.
- 유형 체계는 권장 목록으로 제공하고, 프로젝트가 명시한 체계를 우선한다.
- 문서 간 참조는 티커와 짧은 제목을 함께 적어 오인 가능성을 줄인다.
