# STS 독립 검토 지침

원본 SRS와 STS 초안을 새로운 관점에서 비교한다. 작성자의 해석을 검증 없이 받아들이지 않는다.

## 입력

- 원본 SRS와 버전
- STS 초안
- 승인된 가정 또는 결정

## 검토 항목

### 요구사항과 추적성

- 시험 가능한 요구사항마다 연결된 `TC`가 있거나 검증 공백에 대한 설명이 있다.
- 각 요구사항의 합격 조건이 연결된 사례에서 판정 가능하다. 한 사례가 여러 요구사항을 다루면 각 조건을 따로 확인할 수 있다.
- 각 `TC`가 유효한 요구사항에 연결된다.
- 요구사항·시험 사례 ID 및 참조가 일치한다.
- 불명확하거나 모순된 요구사항은 `ISSUE`로 기록된다.

### 시험 설계

- 필요한 정상 동작을 검증한다.
- 적용 가능한 경계, 빈 값·누락, 잘못된 값, 시간, 상태, 복구, 인터페이스, 권한 조건을 검토한다.
- 결과를 구별하는 데 필요한 조건이 사례나 공백에서 빠지지 않았다. 기법을 사용했다면 해당 요구사항과 입력 특성에 맞는다.
- 기대 결과가 정의된 조건은 필요한 사례에서 확인한다. 정의되지 않은 동작은 결정 전까지 이슈와 검증 공백이다.

### 시험 절차

- 각 사례에 재현에 필요한 선행 조건, 입력·트리거, 단계, 기대 결과, 합격 기준, 근거가 있다.
- 해당할 때 설정, 동작, 확인, 정리가 구분된다.
- 기술한 순서대로 실행할 수 있다.
- 의미 있는 단계마다 관찰 가능한 기대 결과가 있다.

### 요구사항 준수

- 기대 결과는 SRS로 뒷받침되거나 결정 필요로 표시된다.
- 구현에서 추측한 동작을 지어내지 않았다.
- 구현 및 시험 실행 전에 실제 실행이나 코드 커버리지를 주장하지 않는다.

## 검토 결과

`ID`, 검토 분류, 위치, 발견사항, 근거, 권고 조치, 상태를 기록한다. 틀린 요구사항·기대 결과·절차·추적성이나 누락은 `Must Fix`, SRS 정보 부족은 `Clarification Needed`, 명료성·형식 개선은 `Suggestion`으로 분류한다.

마지막에 `Approved`, `Approved with Suggestions`, `Revision Required` 중 하나의 판단과 분류별 개수, 수용한 위험 또는 미결 결정, STS 승인 전에 필요한 후속 조치를 남긴다.
