# 리팩터링

승인된 외부 동작을 유지하며 내부 구조를 바꿀 때 사용한다.

영향 확인 결과 구성요소 경계를 넘거나 공유 인터페이스 변경·재설계가 필요하면 관련 코드 수정 전에 [아키텍처 변경](architecture-change.md)을 수행한다.

1. 유지할 동작 계약과 범위를 명시한다. 호출부와 기존 검사를 추적하고 구조 변경 전에 특성화 검사를 확인하거나 추가한다.
2. `architecting`으로 목표 구조와 줄어들 결합도·복잡성·잘못된 상태를 정한다. 상태나 도메인 관계를 재구성하면 `domain-model-first`를 적용한다. 새 동작이 필요하면 기능 개발 또는 버그 수정으로 보낸다.
3. 여러 구성요소를 바꾸면 `work-decomposition`을 적용한다. 결합된 API와 호출부 변경은 계약을 고정한 통합 담당자가 맡고, 수정 영역과 검사가 분리된 변경만 나눈다.
4. `minimal-change`를 적용해 동작 기준을 통과시키며 작은 구조 변경을 한다. 오래된 경로를 제거하고 같은 범위에서 호출부를 갱신하며, 근거 없는 호환 계층은 만들지 않는다.
5. `prove-real-result`와 `verification`으로 관련 테스트와 실제 타깃 표면에서 전후 동작을 비교한다. 큰 변경은 가능한 경우 동등성 검사나 재생 검사를 사용한다.
6. 전체 diff를 리뷰하고 동작은 바뀌지 않으면서 목표 구조가 개선됐는지 확인한다. 계약, 검사, 리비전, 미확인 증거를 기록하고 인계 전에 `review`를 적용한다.

결과: 구조 변경, 유지한 동작 계약, 동등성 증거, 리뷰 가능한 변경 기록.

코드 작성 전에 `change-impact-check`를 적용해 현재 아키텍처와 영향받는 작업을 확인한다. 범위가 넓어지거나 재설계가 필요하면 `architecting`과 `work-decomposition`으로 작업 경로를 정한다.

## 산출물과 근거 연결

- 승인된 SRS/STS 리비전과 관련 `REQ`·`TC`, 유지할 동작 계약을 확인한다.
- 선택한 `WORK` 범위로 구조 변경을 제한하고 필요한 호출자·인터페이스 이행을 추적성에 기록한다. 무관한 정리는 별도 작업으로 둔다.
- 관련 대상 환경에서 변경 전후 동작을 비교하고 수행하지 못한 검증은 미결로 표시한다.
- 요구사항·인터페이스·시험 기대 결과·수용 기준 변경이 필요하면 [기준선 변경관리](change-control.md)를 따른다. 새 동작은 [피처](feature.md), 결함 수정은 [버그 수정](bug-fix.md)을 따른다.
