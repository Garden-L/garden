# 기능 개발

합의된 목표와 기대 동작의 기준 자료가 있고, 소프트웨어 동작을 추가하거나 변경할 때 사용한다.

영향 확인 결과 구성요소 경계를 넘거나 공유 인터페이스 변경·재설계가 필요하면 관련 코드 수정 전에 [아키텍처 변경](architecture-change.md)을 수행한다.

1. 결과, 사용자 관점의 동작, 인수 조건, 범위, 기준 자료를 명시한다. 중요한 제품·도메인 결정이 빠졌으면 코딩 전에 확정한다.
2. 영향받는 시스템, 호출부, 데이터, 테스트를 추적한다. 중요한 설계 결정에는 `architecting`, 상태·분기 로직에는 `domain-model-first`, 신뢰·표현 경계를 넘는 데이터에는 `boundary-discipline`을 적용한다.
3. `work-decomposition`을 적용한다. 선행 단계, 독립 작업, 공유 변경 상태, 최소 안전 분할을 기록한다. 작거나 강하게 결합된 변경은 담당자 한 명이 맡는다. 경계가 명확하고 독립 검사가 가능하며 수정 소유권이 겹치지 않을 때만 분할한다.
4. 나눈 각 작업에 담당자, 파일 또는 인터페이스, 입력, 결과, 의존성, 검사를 지정한다. 통합과 리뷰는 담당자 한 명이 책임진다. 위임 환경이 없으면 같은 체크포인트에 따라 순차 진행한다.
5. `minimal-change`를 적용한다. `behavior-focused-tests`로 실용적인 동작 검사를 선택하거나 작성하고, 코드 변경 전에 누락 동작을 드러내는지 확인한다. 합의한 범위만 구현하고 승인된 요구사항·결정을 기대 결과의 기준으로 삼는다.
6. 변경을 통합하고 전체 diff를 살핀다. 같은 리비전에서 집중 검사 후 관련 회귀·통합 검사를 실행한다. 실제 동작과 타깃 표면에 `prove-real-result`와 `verification`을 적용하고, 실행할 수 없는 검사는 대기로 표시한다.
7. 변경 범위, 리비전, 검사, 증거, 예외를 작업 기록에 갱신한다. 인계나 릴리스 전에 완료된 diff를 `review`로 검토한다.

결과: 범위가 정해진 기능, 분할 방식과 한 명을 선택한 이유, 동작 증거, 리뷰 가능한 변경 기록.

코드 작성 전에 `change-impact-check`를 적용해 현재 아키텍처와 영향받는 작업을 확인한다. 범위가 넓어지거나 재설계가 필요하면 `architecting`과 `work-decomposition`으로 작업 경로를 정한다.

## 산출물과 근거 연결

- 승인된 `WORK`, SRS, STS의 리비전과 `REQ`·`TC` 연결을 동작 및 수용 기준으로 사용한다.
- 선택한 `WORK` 범위로 변경을 제한한다. 무관한 정리·포맷·이름 변경·재설계는 별도 작업으로 둔다. 필요한 범위 확장은 이유를 기록하고 추적성을 갱신한다.
- 실제 확인 근거를 같은 ID에 연결하고 수행하지 못한 대상 환경 검증은 미결로 표시한다.
- 승인된 요구사항·인터페이스·시험 기대 결과·수용 기준 변경이 필요하면 [기준선 변경관리](change-control.md)를 따른다.
