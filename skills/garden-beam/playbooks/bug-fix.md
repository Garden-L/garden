# 버그 수정

정해진 기대 동작과 비교해 비의도 동작을 재현하거나 조사할 때 사용한다.

영향 확인 결과 구성요소 경계를 넘거나 공유 인터페이스 변경·재설계가 필요하면 관련 코드 수정 전에 [아키텍처 변경](architecture-change.md)을 수행한다.

1. 기대 동작, 영향받는 시스템, 증상, 관련 환경을 확인한다.
2. 가장 적절한 표면에서 실패를 재현한다. 리비전, 설정, 입력, 명령·절차, 기대 결과, 실제 결과를 기록한다.
3. `root-cause-first`를 적용한다. 원인 후보를 추적하고 증거로 제거한다. 확인되지 않은 원인을 전제로 코딩하지 않는다. 기대 동작이 없거나 모순되면 구현 전에 기준의 소유자에게 확인한다.
4. 조사나 수정이 여러 담당자 또는 단계로 나뉘면 `work-decomposition`을 적용한다. 재현과 강하게 결합된 수정은 한 담당자가 맡고, 인계가 명확한 독립 조사·결과물만 분리한다.
5. `minimal-change`를 적용한다. `behavior-focused-tests`로 실용적인 회귀 검사를 골라 수정 전 실패를 확인한 뒤 증거가 뒷받침하는 최소 수정을 한다.
6. 같은 표면과 리비전에서 원래 재현 절차를 다시 실행한 뒤 관련 회귀 검사를 한다. `prove-real-result`와 `verification`을 적용하고 확인하지 못한 환경은 대기로 기록한다.
7. 변경 기록을 갱신하고 완료된 diff를 `review`로 검토한다.

결과: 증상, 입증된 원인, 제한된 수정, 재현 증거, 남은 검사.

코드 작성 전에 `change-impact-check`를 적용해 현재 아키텍처와 영향받는 작업을 확인한다. 범위가 넓어지거나 재설계가 필요하면 `architecting`과 `work-decomposition`으로 작업 경로를 정한다.

## 산출물과 근거 연결

- 적용 SRS/STS 리비전, 관련 `REQ`·`TC`, 증상, 타깃 환경을 확인하고 승인된 기대 결과에 대해 재현한다.
- 원인을 기록하고 수정 범위를 해당 `WORK`와 추적성에 묶는다. 무관한 정리·포맷·이름 변경·재설계는 별도 작업으로 둔다.
- 같은 환경에서 재현 절차와 관련 회귀 확인을 반복하고 로컬 근거와 필요한 대상 환경의 근거를 구분한다.
- 승인된 기대 결과가 없거나 충돌하거나 변경이 필요하면 [기준선 변경관리](change-control.md)를 따른다.
