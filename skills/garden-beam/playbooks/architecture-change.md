# 아키텍처 변경

`change-impact-check`에서 작업이 구성요소 경계를 넘거나 공유 인터페이스를 바꾸거나 재설계가 필요하다고 확인되면 사용한다. 영향을 받는 영역의 코드 변경 전에 수행한다.

1. 영향받는 모듈, 호출자, 인터페이스, 상태, `REQ`/`TC` 연결, `WORK` 패키지를 확인한다. 확인된 영향과 미지의 부분을 구분한다.
2. `architecting`을 적용해 목표 경계와 책임을 선택한다. 변경을 결정하는 데 필요한 범위에서 타입, 시그니처, 모듈 배치, 인터페이스 관계를 스케치한다.
3. 현재 구조와 목표 구조를 비교한다. 이행 순서, 의존성, 공유 파일, 각 단계에서 승인된 동작의 유지·변경을 확인할 방법을 정한다.
4. `work-decomposition`으로 경계가 분명한 작업 패키지, 통합 책임자, 확인 방법을 정한다. 승인된 SRS, STS, 인터페이스, 수용 기준이 바뀌면 영향받는 구현 전에 [기준선 변경관리](change-control.md)를 따른다.
5. 선택한 구조와 작업 경계, 검증 경로를 가지고 [피처](feature.md), [버그 수정](bug-fix.md), [리팩토링](refactoring.md) 플레이북으로 돌아간다.

산출물: 영향 범위, 목표 구조, 이행 순서, 작업 경계, 남은 결정 사항.
