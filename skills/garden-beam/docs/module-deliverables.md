# 모듈 산출물 연결 기준

모듈 작업에서 요구사항, 시험, 코드, 검증 근거를 만들 때 사용한다. 선택한 [플레이북](../playbooks/)이 필요한 산출물과 인계 조건을 정한다. 이 문서는 그 산출물 사이의 연결과 상태 의미를 정하며, 모든 모듈에 아래 문서를 전부 요구하지 않는다.

## 공통 연결

범위 안의 원본 의무에서 파생된 `REQ`, 계획된 `TC`, 해당 `WORK`, 변경한 코드·시험, 실제 근거까지의 경로를 유지한다. 안정적인 ID와 원본·산출물 리비전을 사용한다. 빠진 연결은 이유와 함께 대기 또는 범위 밖으로 표시한다. 모호성·충돌·결정은 하나의 정본 `ISSUE` 기록에 두고 영향받은 산출물에서 연결한다.

| 필요한 작업 | 산출물과 유용한 내용 |
| --- | --- |
| 요구사항 정의 | 출처에 연결된 `REQ`, 관찰 가능한 조건, 가정, 미결 이슈가 있는 SRS |
| 시험 설계 | `REQ`에 연결된 `TC`, 설정·자극·기대 결과·합격 기준·시험 공백이 있는 STS |
| 코드 변경 | 수용 기준, 영향받는 `REQ`·`TC`, 코드와 확인 방법을 연결한 범위가 정해진 `WORK` 기록 또는 동등한 산출물 |
| 승인 기준선 변경 | 영향받는 요구사항·시험·작업과 후속 작업 재개 조건을 연결한 결정·영향 기록 |
| 실행한 검증 | 환경, 리비전, 절차, 기대·관찰 결과, 근거 위치, 미수행 확인 |
| 모듈 인계 | 실제 생성한 산출물을 연결하고 근거가 뒷받침하는 결론과 공백을 표시한 목차 또는 추적성 보기 |

대상 프로젝트에 이미 정한 이름과 위치가 있으면 그것을 사용한다. 코드와 자동화 시험은 일반 소스 트리에 둔다. 로그나 추적은 안정적인 위치에 보관하고 연결한다. 계획한 검사는 실행 근거가 아니다. 로컬 결과와 필요한 통합·대상 환경·릴리스 근거를 구분한다.

## 결정과 결론

`ISSUE`에 상태를 표시한다면 `Open`은 수용된 해결이 없음, `Decided`는 책임자의 선택, `Applied`는 해당 산출물이나 코드의 변경, `Verified`는 근거에 대조해 결과를 확인함을 뜻한다. 이전 결정을 대체해도 그 이력을 보존한다.

모듈의 결론은 선언한 범위와 환경에 대해서만 말한다. `Verified`에는 뒷받침되는 요구사항, 해당하는 시험·작업 연결, 필요한 환경에서 실행한 근거가 필요하다. `Verified with gaps`는 대기·미결 의무와 영향을 밝힌다. `Not verified`는 근거가 전달 결론을 뒷받침하지 못한다는 뜻이다. 로컬 결과를 실행하지 않은 대상 환경이나 릴리스의 결과로 확대하지 않는다.

## 예시 배치와 검사

[속도 신호 예제](../examples/speed-signal/README.md)는 `docs/modules/<module>/`에 번호를 붙인 SRS, STS, 준비성, 구현, 검증 폴더를 사용한다. 이는 하나의 완성된 인계 예시이며, 실제 프로젝트에서는 동등한 위치를 써도 된다. 예제의 [커버리지 보고 도구](../scripts/report-module-coverage.py)는 기록된 연결에서 `completion-report.md`를 만들고, [구조 검사 도구](../scripts/validate-module-delivery.py)는 예제의 전체 파일 묶음과 ID를 검사한다. 이 검사는 요구사항의 의미나 타깃 동작을 증명하지 않는다. 실제 작업의 산출물과 확인 방법은 선택한 플레이북을 따른다.
