# Programming Coursebook Authoring

이 스킬은 특정 언어나 프레임워크의 강의를 설명하는 스킬이 아니다. 프로그래밍 주제를 학습자가 따라 할 수 있는 책과 실습 프로젝트로 바꾸는 저작 워크플로다.

핵심 원칙은 다음이다.

```text
학습 목표
→ 선수 지식
→ 설계할 시스템
→ 요구사항과 사용 사례
→ 완료 조건
→ 개념 설명
→ 단계별 실습
→ 과제와 체크포인트
→ 회고와 다음 장 연결
```

책의 설명, 저장소의 파일, Notion의 장 페이지는 같은 학습 흐름을 표현해야 한다.

## 언제 사용하는가

다음 요청에 사용한다.

- 프로그래밍 책이나 온라인 강의의 전체 커리큘럼을 만들 때
- 개념 설명과 직접 작성하는 실습 프로젝트를 함께 설계할 때
- 기존 프로젝트를 학습용 장·절과 단계별 파일로 바꿀 때
- Notion에 코스 메인 페이지와 장별 서브 페이지를 만들 때
- 학습자 과제, 체크포인트, 제출 기준, 회고 질문을 설계할 때

Rust, Tokio, SOLID, 코드 스멜, 리팩터링은 이 스킬의 전제가 아니다. 주제와 학습 목표에 도움이 될 때만 선택형 교육 모듈로 사용한다.

## 먼저 정할 입력

정보가 없다고 무조건 질문하지 않는다. 아래 정보 중 답에 따라 코스 구조가 크게 달라지는 것만 확인하고, 나머지는 합리적인 제안으로 채운다.

- 주제와 최종적으로 만들 학습 결과물
- 대상 학습자와 현재 수준
- 사용 언어, 런타임, 도구, 버전
- 예상 학습 기간과 한 장에 사용할 시간
- 최종 프로젝트 또는 학습자가 수행할 실제 작업
- 저장소를 새로 만들지, 기존 저장소에 추가할지
- Notion에 실제로 쓸 것인지, 먼저 문서 구조만 설계할 것인지

언어와 프레임워크를 사용자가 정했다면 기존 프로젝트의 도구와 규칙을 따른다. 정하지 않았다면 설계에서 선택한 이유와 가정을 기록한다.

## 필수 산출물

코스북을 만들 때 아래 결과를 모두 만든다. 사용자가 특정 산출물을 제외한다고 명시한 경우에만 생략한다.

### 1. 책 전체 구조

```text
코스북 메인
├── 코스 소개와 학습 방법
├── 환경 설정
├── 전체 목차
├── 선수 지식과 권장 학습 순서
├── 01장
│   ├── 1.1 절
│   ├── 1.2 절
│   └── 실습과 과제
├── 02장
└── 최종 프로젝트와 다음 학습
```

고정된 장 수를 임의로 정하지 않는다. 대신 전체 목표를 달성하는 데 필요한 장을 나누고, 장 사이의 의존성과 순서를 설명한다.

전체 목차에는 다음을 포함한다.

- 코스 제목과 한 문장 설명
- 대상 학습자
- 코스를 끝낸 뒤 할 수 있어야 하는 일
- 선수 지식
- 개발 환경과 도구 요구사항
- 장별 제목과 핵심 질문
- 예상 학습 시간
- 최종 프로젝트 또는 완료 결과물

### 2. 장별 설계

각 장은 반드시 다음 순서로 작성한다.

1. 학습 목표: 학습자가 관찰 가능한 행동으로 표현한다.
2. 선수 지식: 이 장을 시작하기 전에 알고 있어야 할 것과 이전 장 링크를 적는다.
3. 설계 대상: 무엇을 만들거나 분석할지, 범위와 비범위를 적는다.
4. 기능 요구사항: 시스템이 제공해야 할 기능을 사용자 관점으로 적는다.
5. 사용 사례: 입력, 흐름, 결과, 오류 상황을 구체적으로 적는다.
6. 완료 조건: 테스트나 관찰 가능한 결과로 판단할 수 있게 적는다.
7. 개념: 첫 코드에서 필요해지는 직전에 설명한다.
8. 단계별 실습: 각 단계의 목적, 수정할 파일, 실행 명령, 기대 결과를 적는다.
9. 과제: 학습자가 직접 바꾸거나 확장할 요구사항을 적는다.
10. 체크포인트: 다음으로 넘어가기 전 확인할 결과를 적는다.
11. 회고: 설계 선택, 실패 원인, 남은 질문을 돌아보게 한다.

장별 템플릿은 [references/coursebook-template.md](references/coursebook-template.md)를 사용한다.

### 3. 실습 프로젝트

장별로 학습자가 실제로 열고 수정할 수 있는 프로젝트 디렉터리와 파일을 만든다.

```text
exercises/
  01-topic/
    README.md
    project-config
    src/
      01_initial_draft/
        README.md
        main-or-lib
      02_core_requirement/
        README.md
        main-or-lib
      03_change_request/
        README.md
        main-or-lib
      04_responsibility_refinement/
        README.md
        main-or-lib
      05_final_reference/
        README.md
        main-or-lib
    tests/
    assignments/
```

언어에 따라 디렉터리와 파일 확장자는 바꿀 수 있지만, 각 단계에는 반드시 다음 정보가 있어야 한다.

- 단계의 학습 목적
- 이전 단계에서 무엇이 바뀌었는지
- 학습자가 작성해야 하는 TODO 또는 변경 지점
- 실행·테스트 명령
- 통과 기준
- 다음 단계로 넘어갈 때 확인할 질문

단계 이름은 `v0`, `v1`, `v2`, `step1`, `final2`처럼 의미가 없는 이름을 기본값으로 사용하지 않는다. 단계의 교육 목적을 드러내는 이름을 쓴다. 예시는 다음과 같다.

- `01_initial_draft`: 가장 단순한 초안으로 문제를 경험한다.
- `02_core_requirement`: 핵심 요구사항을 만족시킨다.
- `03_change_request`: 새 요구사항이 기존 설계에 미치는 영향을 확인한다.
- `04_responsibility_refinement`: 변경 이유가 다른 코드를 분리한다.
- `05_policy_injection`: 바뀌는 정책이나 외부 의존성을 주입한다.
- `05_final_reference`: 학습자가 작성한 코드와 비교하는 참고 구현이다.

모든 장에 같은 단계 수를 강제하지 않는다. 단계가 늘어날 때마다 어떤 학습 질문을 해결하는지 설명한다.

### 4. Notion 책 구조

사용자가 Notion 작성을 요청했거나 연결된 Notion 작업공간이 있으면 다음을 실제 페이지로 만든다.

```text
코스북 메인 페이지
├── 코스 개요
├── 학습 방법과 환경 설정
├── 전체 목차
├── 01장 서브 페이지
├── 02장 서브 페이지
└── 최종 프로젝트 서브 페이지
```

메인 페이지에는 저장소 링크, 전체 목차, 학습 순서, 공통 환경 설정을 둔다. 장 서브 페이지에는 해당 장의 README와 같은 장 번호·제목을 사용하고 다음을 포함한다.

- 학습 목표와 선수 지식
- 설계 대상과 범위
- 기능 요구사항, 사용 사례, 완료 조건
- 개념 설명
- 실습 단계별 저장소 파일 링크
- 과제와 체크포인트
- 회고 질문
- 선택형 설계 모듈

Notion을 실제로 수정할 때는 대상 페이지를 먼저 읽고, 기존 하위 페이지와 내용을 보존한 뒤, 저장 후 다시 읽어 링크와 구조를 확인한다. 연결된 Notion이 없으면 페이지 트리와 각 페이지 내용을 Markdown으로 산출하고, 실제 동기화가 필요한지 명시한다.

## 단계별 실습을 설계하는 방법

각 장의 실습은 다음 질문에 답해야 한다.

```text
학습자는 지금 무엇을 만들고 있는가?
왜 이 기능이 필요한가?
현재 요구사항은 무엇인가?
완료됐다고 판단할 증거는 무엇인가?
어떤 파일을 열고 어떤 코드를 작성하는가?
실패하거나 변경될 때 무엇을 관찰하는가?
다음 단계에서 무엇을 개선하는가?
```

초안 단계는 일부러 단순하게 만들 수 있다. 그러나 단순함을 무조건 나쁜 코드라고 설명하지 않는다. 초안의 목적이 요구사항을 빠르게 확인하는 것인지, 학습자가 문제를 관찰하는 것인지 먼저 밝힌다.

설계 개선을 포함하는 코스라면 개선 전후를 나란히 비교한다. 코드 스멜, SOLID, 리팩터링, 테스트, 아키텍처 같은 개념은 다음 조건을 만족할 때만 포함한다.

- 실제 변경 요구사항이 기존 구현의 한계를 드러낸다.
- 해당 개념이 왜 필요한지 코드와 테스트로 관찰할 수 있다.
- 개념을 적용하지 않는 대안과 비용도 설명할 수 있다.

원칙 이름을 먼저 나열하고 코드에 억지로 끼워 넣지 않는다. 예를 들어 SOLID를 다루려면 “새 구현을 추가할 때 기존 알고리즘을 수정하지 않아야 한다” 같은 구체적인 변경 요구사항에서 시작한다.

## 과제·체크포인트·회고

각 장의 과제는 읽기만 해도 답을 알 수 있는 질문이 아니라 학습자가 코드를 바꾸고 결과를 확인하는 작업이어야 한다.

과제에는 다음을 적는다.

- 시작 파일
- 학습자가 구현할 요구사항
- 변경 가능한 파일과 변경하면 안 되는 파일
- 테스트 또는 실행 명령
- 제출하거나 확인할 결과
- 확장 과제

체크포인트는 “이해했는가?”가 아니라 관찰 가능한 결과로 작성한다. 예를 들어 “입력이 비어 있을 때 오류를 반환하고 테스트가 통과한다”처럼 쓴다.

회고 질문은 다음 중 장에 맞는 것을 선택한다.

- 처음 구현에서 가장 쉽게 만든 부분과 가장 위험한 부분은 무엇인가?
- 요구사항이 하나 추가되면서 어떤 파일이 함께 바뀌었는가?
- 어떤 책임을 분리했으며, 분리하지 않았을 때의 비용은 무엇인가?
- 이번 추상화가 실제 변경을 줄였는가, 아니면 복잡성만 늘렸는가?
- 다음 장에서 바뀔 가능성이 높은 부분은 어디인가?

## 출력 계약

코스북 설계 결과를 다음 순서로 출력한다.

1. 코스 브리프
2. 대상 학습자와 선수 지식
3. 환경 요구사항
4. 최종 학습 결과물
5. 전체 목차와 장·절 구조
6. 장별 설계 문서
7. 실습 프로젝트 디렉터리 트리
8. 단계별 파일 목록과 각 파일의 목적
9. 과제·체크포인트·회고 질문 표
10. Notion 메인 페이지와 장 서브 페이지 트리
11. 선택한 교육 모듈과 선택 이유
12. 검증 결과와 남은 결정 사항

## 품질 검증

완료 전에 다음을 확인한다.

- 모든 장의 학습 목표가 관찰 가능한가?
- 선수 지식이 실제 첫 코드와 맞는가?
- 요구사항과 사용 사례가 구현 파일과 연결되는가?
- 완료 조건이 실행 또는 테스트로 검증 가능한가?
- 모든 주요 개념에 직접 해보는 실습이 있는가?
- 단계 이름만 보고도 단계의 학습 목적을 알 수 있는가?
- 과제와 체크포인트가 학습 목표를 검증하는가?
- Notion 장 페이지와 저장소 장 구조가 일치하는가?
- 선택형 이론이 실제 코드나 요구사항에 의해 정당화되는가?
- 학습자가 다음 행동을 파일 경로와 명령으로 알 수 있는가?

가능한 프로젝트에서는 언어별 포맷터, 테스트, 린터를 실행하고, 문서에 적힌 명령도 실제로 검증한다. 단순한 파일 존재 확인만으로 완료를 주장하지 않는다.

## Git 경계

기존 프로젝트의 변경과 새 스킬 저장소의 변경을 분리한다. 사용자가 GitHub 게시를 명시적으로 요청한 경우에만 새 스킬 저장소에 커밋·푸시한다. 다른 저장소의 변경을 함께 커밋하거나, 사용자가 요청하지 않은 프로젝트 변경을 커밋하지 않는다.
