# TICKER Rules

TICKER는 문서·대화·이슈·도구 사이에서 하나의 항목을 안정적으로 가리키기 위한 식별자다. STS/SRS는 적용 가능한 예시일 뿐이며, 이 스킬은 특정 문서 형식·저장소·이슈 트래커·업무 프로세스를 강제하지 않는다.

## Core rules

1. **필요할 때만 만든다.** 여러 위치에서 다시 참조하거나, 변경·검토·추적이 필요한 항목에만 TICKER를 부여한다. 단순 문장, 일회성 메모, 이미 충분히 식별 가능한 제목에는 만들지 않는다.
2. **한 항목에 하나만 부여한다.** 같은 항목에 여러 TICKER를 만들지 않는다. 기존 식별자가 안정적이고 범위가 명확하면 그것을 TICKER로 재사용할 수 있다.
3. **의미가 바뀌면 재사용하지 않는다.** 제목·상태·담당자·우선순위가 바뀌어도 TICKER는 유지한다. 요구사항이 다른 요구사항으로 바뀌거나 결함이 별도 요구사항이 되는 등 대상의 본질이 바뀌면 새 TICKER를 만들고 이전 항목과 연결한다.
4. **티커에 변하는 정보를 넣지 않는다.** 상태, 날짜, 담당자, 우선순위, 버전, 제목을 TICKER에 포함하지 않는다.
5. **범위를 명확히 한다.** TICKER는 프로젝트 또는 문서 집합 안에서 유일해야 한다. 다른 범위에서 인용할 때는 프로젝트/문서명, 링크 또는 외부 시스템 ID를 함께 적는다.
6. **조직 규칙이 있으면 우선한다.** 이미 정해진 접두사, 번호 체계, 외부 시스템 ID가 있으면 이 권장 형식보다 기존 규칙을 따른다.

## Recommended form

권장 표기는 `<TYPE>-<IDENTIFIER>`다.

```text
REQ-014
ISSUE-027
BUG-003
```

`IDENTIFIER`는 해당 범위에서 충돌하지 않는 안정적인 값이어야 한다. 숫자 순번을 쓸 경우 병렬 생성이 가능한 등록 체계를 사용하고, 단순히 “다음 번호”를 추측해 충돌시키지 않는다. 충돌 여부를 확인할 수 없으면 기존 등록부·트래커·문서 규칙을 확인하거나, 사용 중인 시스템이 제공하는 ID를 그대로 사용한다.

## Type meanings

유형은 현재 항목의 추적 목적을 설명하는 권장 분류다. 프로젝트가 더 적합한 유형을 정의하면 그 체계를 따른다.

| Type | Use for | Example |
|---|---|---|
| `REQ` | 충족되어야 하는 기능·품질·제약·조건 | `REQ-014` |
| `ISSUE` | 조사·논의·판단이 필요한 질문, 불일치, 장애물 | `ISSUE-027` |
| `BUG` | 기대 동작과 실제 동작의 차이로 확인된 결함 | `BUG-003` |
| `TASK` | 결과물이 분명한 실행 작업 | `TASK-041` |
| `RISK` | 아직 발생하지 않았지만 목표에 영향을 줄 수 있는 위험 | `RISK-008` |
| `DECISION` | 여러 선택지 중 확정된 판단과 그 근거 | `DECISION-006` |
| `CHANGE` | 승인·추적해야 하는 변경 제안 또는 변경 기록 | `CHANGE-012` |

`ISSUE`는 “무엇인지 아직 확정되지 않았지만 추적이 필요한 것”에 사용한다. 재현 가능한 결함이 확인되면 새 `BUG`를 만들거나, 조직 규칙에 따라 기존 `ISSUE`를 `BUG`로 전환한다. 어느 경우든 전환 관계를 기록하고 두 항목이 동시에 같은 사실을 대표하지 않게 한다.

## Creation and reference

새 TICKER를 만들 때는 최소한 다음을 함께 기록한다.

```text
REQ-014 — 사용자는 저장된 검색 조건을 다시 불러올 수 있어야 한다.
```

필요하면 상태·우선순위·담당자·출처·관련 티커를 별도 필드로 둔다. 이 정보가 TICKER 문자열에 들어가서는 안 된다.

다른 문서에서 참조할 때는 다음처럼 TICKER와 짧은 제목을 함께 적는다.

```text
REQ-014(저장된 검색 조건 재사용)을 만족해야 한다.
BUG-003은 REQ-014의 구현에서 발견되었다.
```

같은 문자열이 다른 범위에 존재할 수 있으면 다음처럼 범위를 보강한다.

```text
PAYMENTS/REQ-014
```

## Review checklist

TICKER를 만들거나 검토할 때 다음을 확인한다.

- 이 항목을 나중에 다시 찾아야 하는가?
- 같은 범위에 이미 같은 대상을 가리키는 TICKER가 있는가?
- 유형이 대상의 현재 추적 목적과 맞는가?
- 티커가 제목·상태·담당자처럼 바뀌는 정보를 포함하지 않는가?
- 범위 밖에서 참조해도 출처와 충돌을 구분할 수 있는가?
- 관련 TICKER, 상위 요구사항 또는 전환 관계가 필요한가?

정보가 부족하면 번호나 유형을 추측하지 말고, 기존 등록부·프로젝트 규칙·문서 맥락을 확인한다. TICKER를 생성할 권한이나 등록 위치가 없으면 후보를 제안하되 확정된 식별자인 것처럼 표현하지 않는다.

## STS/SRS examples

다음은 적용 예시이며 STS/SRS가 아닌 문서에도 같은 원칙을 적용한다.

```text
REQ-014  사용자는 저장된 검색 조건을 다시 불러올 수 있어야 한다.
ISSUE-027  검색 조건의 만료 정책이 정의되지 않았다.
BUG-003  만료된 검색 조건이 검색 목록에 계속 표시된다.
DECISION-006  만료된 조건은 30일 후 자동 삭제한다.
```

이 예시에서 `ISSUE-027`은 정의 공백을 추적하고, `BUG-003`은 확인된 동작 결함을 추적하며, `DECISION-006`은 그에 대한 확정 판단을 추적한다. 서로 다른 목적의 항목을 하나의 TICKER에 합치지 않는다.
